
### 1. 简单介绍一下agent。单智能体和多智能体的区别？
Agent一般是指既能接收输入（像数据、用户请求），又能根据一定的规则、模型或算法，自动做出决策，然后可以执行某些操作的系统。

单智能体系统就是一个智能体单独行动，从感知输入、做决策、执行任务都自己搞定。多智能体系统是指有好几个智能体一起工作，每个智能体会被分配到任务链路上的某一个环节，大家之间可以协作、沟通，共享部分的上下文。它们共同作用，去解决一个更复杂的大任务。

### 2. 如何减轻大模型幻觉？
检索增强生成（RAG）：让模型先去查资料，比如知识库、数据库或者互联网，再结合新查到的信息生成回答。
Prompt 优化：规范化 Prompt，用禁令标签明确告诉模型要根据事实、不要乱编。
多轮确认：让模型自检、反思或者多问几轮。
人工审查：加入human in loop，执行事情之前让人类确认把关。

### 3. 如何提升生成质量？
从大模型能力出发，保证数据质量和多样性，用干净、丰富且高质量的数据来训练或者微调，从根本上提升模型能力。
从prompt出发，设计好 Prompt的骨架，最好用结构化语言，不同的指令进行分类，可以加入高质量的few-shot等。
引入rag：配合知识库、数据库或 API，把检索和生成结合，让模型生成更有事实依据的内容。
从agent出发，对输出进行后处理和自检：让模型自己复查输出，或者用其他模型/规则做校验、过滤。在多agent结构下，做好各环节agent的监控，方便对他们进行筛查，然后做优化。

### 4. 什么是mcp？跟本地工具的区别？
MCP是一套标准，用来让不同的agent、本地工具、插件等可以互相“说话”，通过消息格式来完成调度、数据交换和功能调用，本质上是一种传输结构化信息的网络请求。

本地工具大多是通过进程调用、文件读写等方式工作，只能在本机交互。用了MCP协议，agent和工具可以不管是在本地还是远程，只要遵守协议格式，就能通过消息来协同工作。意味着MCP协议让agent可以使用的工具不再局限于本地，而是可以使用别的服务器提供的服务，同时也可以把本地服务暴露给别的服务器。

### 5. 什么是skill？原理流程是什么？skil的优势是什么？
skill实际上就是把一整套工作流程“封装”成技能，一份说明文档。Skill 里面已经预设了流程和执行顺序，让大模型不用每次从零推理怎么做，而是直接“走流程”。

在选择skill的时候，大模型只需要获取各个skill的描述不用管背后细节，相当于把大量的prompt和工具描述信息封装起来，达到渐进式披露，缩短大模型首次需要的上下文的长度。而且skill大大降低了 LLM 的调度和决策难度，让大模型更多是“触发流程”：只要知道何时、为何触发 skill，剩下的都靠 skill 内部工作流处理。

### 6. 什么是cli？
 agent cli就是可以像用普通命令行工具一样，通过输入指令和参数，来驱动 agent 完成任务。cli对比mcp，token消耗更小，cli可以用渐进式披露的方法，让agent自行查阅命令行的具体使用；并且cli天生支持管道符来把多个任务组成流水线，直接一次调用完成，而不需要反复多次调用工具。
 但MCP生态一般有一整套监控、认证、权限、日志等系统，方便团队统一运维和安全管控，并且mcp协议支持异步消息传递、更复杂的工作流编排。而CLI调用多半是同步、阻塞的，难以胜任复杂流程管理。

### 7. 智能体有哪些架构？
ReAct（Reason+Act）架构，模型一边思考（推理），一边决定要不要采取行动（比如调用工具/skill），然后根据环境反馈再继续推理并行动。灵活迭代、强可解释性、适合复杂多步推理。

Plan-Execute（PE）架构，agent先生成一个完整计划（Plan），再沿计划序列逐步调用工具/skill（Execute），能一次性搞定复杂任务，有整体全局感，但环境变化时需重新调整计划。

Plan-Reason-Execute/Planner-Controller (PRe, P-A-R) 架构，分工更细，模型分三步（或多个agent协作）：规划任务（Planner/Plan）分析每步（Reason）实际执行（Execute/Act），复杂多步流程细分，有助于解释、debug和自我纠错。

### 8. 多智能体如何设计架构？
明确需求：先搞清楚你的多Agent系统是要干啥，明确业务流程和任务拆解，决定Agent之间的基本分工以及agent之间交换的状态。
角色设计：按照目标，把任务拆分成合适的小块，每块交给一个agent。定义每个agent的“技能点”：能做什么、能接受什么输入/输出什么结果。
任务调度：中心化还是去中心化？中心化调度适合流程线，平等适合自治协作。
监控日志：给每个agent都加监控（比如状态心跳、调用链追踪、日志上传），快速定位问题。
安全与权限：细分各agent的可访问资源、接口权限，设立访问控制。要有上下文审计和防护机制。
未来维护：新加agent像插积木一样简单，不影响老系统，保证未来业务快速变化和扩展。

### 9. ReAct框架怎么用？在实际开发中，如何保证思考和行动不脱节？
ReAct（Reason + Act）框架的本质就是：agent一边“思考”（Reason），一边“行动”（Act），循环迭代直到完成任务。典型用法如下：
输入任务/问题：用户给agent一个目标。
agent推理：模型分析，决定接下来要干什么。
行动（调用工具/Skill）：agent用API/Skill，得到结果。
再推理：基于查到的数据再思考，下一步该怎么办——比如“需要判断订单状态”。
再行动：比如判断后决定“发通知”，于是调用发通知的API。
循环迭代：重复“推理→行动→再推理”直到任务搞定或agent判断完成。

用Prompt明确流程，每一步都“推理完才行动，行动后要反馈再思考”。每次action都要求返回明确的执行结果，推理阶段必须“读取”最新的执行结果再决定下一步，避免上一步做了啥自己都不清楚。给每个ReAct loop限制最大轮数或终止条件，防止“死循环”或逻辑飘走，确保行为始终受控。把每一次“思考”和“行动”都详细记录，便于调试和复盘，保证哪里脱节一查就知道。

### 10. function call和工具调用的区别？
function call指的是大模型能通过结构化的数据格式，来调用外部函数。工具调用指Agent可以调用的所有“外部能力”。可以是函数、API、CLI命令、第三方插件，甚至是另一个Agent。

### 11. ReAct和cot有什么区别？
cot让模型在回答问题时，**写下自己的推理链路**，把一步步思考过程“摊开”来写——比如像写解题步骤。这样增强推理能力，输出可解释性好，易debug。CoT 通常只负责思考，不主动操作外部工具，靠模型记忆和推理本身。
ReAct不光让模型有“思维链”，还让它可以“行动”—主动去调用工具（Tool/Skill）查信息、执行操作，再继续思考，实现闭环.兼顾“推理”和“执行”。
CoT 是“自问自答式思考链”，只推理，不行动；ReAct 是“思考+执行闭环”，模型能推理、能用工具、能根据反馈持续调整思路，适合Agent实战应用。

### 13. few-shot是什么、他们是怎么提升输出质量的？在prompt设计里面怎么组合使用？
few-shot 指的是在提示（prompt）中给大模型几个有代表性的范例，让模型“举一反三”按例子来回答问题或执行任务。
范例约束：模型借助例子“学到”格式、思路、风格，减少发挥过头、答非所问。
降低幻觉：通过范例收敛输出，让模型更“照葫芦画瓢”。
适应新任务：只要你准备的例子针对性强，就能很快“微调”模型行为（如代码风格、摘要结构、任务步骤）。

### 14. prompt如何压缩？
**分层优先删减**
把重要指令、关键信息、必要范例/上下文排在前面，“非核心信息”优先删。优先保留最新上下文、
**结构和内容整理**
去掉重复描述、格式说明。多条风格类似的few-shot例子，筛选“最典型/通用”几条即可，或合并成更简约的范例。
精简问题描述：只保留关键实体、目标、限制条件，把无关的修饰性内容去掉。
**智能摘要与自动压缩**
大模型自身做摘要：让模型自己做关键信息抽取，自动生成浓缩版内容。
**技术和工具手段**
Token-level裁剪：对Tokens长内容用切割（比如分块、滑窗、截断等），控制进模型前的token总数。只提关键信息点，替代冗长上下文。
**高阶trick**
类似内容合并为一行。	少shot优先：few-shot从“多条典型”只留极具代表性的1-2条（One/Few-shot），其余复用或融合。格式紧凑，去掉多余空格、换行、废说明。

### 15. 多个agent持续运行，每天产生几千条轨迹，每天需要报告哪些agent出现了问题，怎么设计监控。
首先明确目标，我们要检测agent的健康（存活/崩溃/掉线），然后异常轨迹（如超时、失败、重复、异常终止）以及关键业务指标/自定义异常状态。那么需要报告的就是哪些agent今天出现过问题（出问题的时间、类型、频率等），问题的上下文轨迹（排查依据）。
每条轨迹用唯一ID，结构标准化（如 JSON），字段包含 agent_id、轨迹起止时间、关键事件、状态码、错误码、上下游信息等。
我们可以在每个agent运行时埋点，采用异步批量上报方式，防止阻塞主流程，记录agent的结构化信息，然后把日志分天数打到统一日志系统。选型支持高写入、高查询吞吐的分布式日志/时序数据库，如ElasticSearch。
设置一些告警条件，比如agent心跳丢失N分钟视为掉线、日志轨迹中失败/超时比例超过阈值、出现指定严重错误类型、单个轨迹超时、频繁重启等。

### 16. openclaw有了解吗？有什么可以借鉴的？
网关鉴权分流。
适配器拆分消息来源，转化成结构化语言。
维护工具表，根据场景挑选工具注入prompt。
Memory Flush/Replay 机制：

对历史长对话/执行链路做摘要，保留核心结论和关键参数。
通过检索式方法（如 RAG）动态查回相关 memory 注入 prompt，保证 LLM 能获取到所需关键信息。

### 18. claude code有了解吗？有什么可以借鉴的？为什么他不用rag而用grep来检索代码？
1. 语义聚合的上下文检索与管理
不是单纯全文检索或词面匹配，而是结合语义理解、依赖关系和模块结构，从整个代码库中智能选取与用户问题最相关的代码片段、依赖、注释，动态聚合成高质量的上下文。

2. 智能上下文摘要与结构化提示
对于长代码或大仓库，采用自动摘要和结构化标注（如代码区块、文件/模块注释、接口说明），在信息带宽有限的情况下优先保留关键信息、过滤冗余内容，并以有利于 LLM 理解的格式注入模型。

3. 动态、多轮协同上下文调整
结合用户每次提问意图和历史多轮上下文，实时调整与补充代码片段，实现上下文内容的增量追踪和连续理解，从而支持复杂跨文件、跨模块的问题解答。

1. 最小化敏感信息暴露（上下文精筛）
Claude 的上下文检索和聚合会有意识地过滤、拒绝或脱敏包含凭证、密码、API Key、个人信息等敏感数据的代码段，降低泄露风险，避免无关或高危内容被纳入模型输入与响应。

2. 权限感知与隔离机制
在企业/团队场景下，Claude 支持基于用户权限和代码可见性精准筛选上下文，仅检索和返回当前会话用户有权限访问的代码片段，防止信息越权及横向代码窃取，支持数据隔离、多租户安全。

1. 上下文定制与智能记忆
Claude 能根据不同用户、项目、个人编码习惯、历史对话记录（多轮上下文等）自动适配和定制上下文检索范围与聚合规则，实现为每个用户动态“量身定制”最相关的代码片段和信息，持续优化理解效果。

### 19. 平时怎么vibe coding？遇到的最大问题是什么？
一般我会先把项目需求/README/接口定义写好，让AI知道我要做什么，能补全和建议得更准。
拆分大任务为几步，每写一块就让AI先给出他的方案，然后讨论过后得到一个合适的方案之后，在让AI给出实现流程，仔细审查没问题之后，再让其实现。
实时让AI写单测模版和用例，顺便查一下边界情况。
可以每实现一部分，就让AI补文档注释、接口说明、README 示例。
有时候团队协作时，直接用AI提供review建议，或者参考建议优化提交说明。
遇到难debug的问题，用AI做初步排查和定位思路。

AI生成代码虽然快，但有时会出错或者胡乱编造，得谨慎review。
AI因为上下文限制，无法记住所有实现过的东西，有时候会前后矛盾改以前测试过没问题的代码，要同步记录开发历史记录，让AI时刻回顾。
对逻辑复杂的业务，一定要让AI有仔细的方案和实现流程，以及完整的接口文档，再让其实现，对我来说文档编写的需求会更大。

### 20. 未来agent产品的走向和核心竞争力是什么？
未来的 agent 产品一定会越来越“垂直化+智能化+可控化”，并且是真正承担生产力。
**数据专有化 & 高质量知识库**
搞定私域数据深度接入、高质量高安全的知识/工具对接，做出真正有长期价值的 agent 产品。
**效果可追踪、过程可控**
能给出流程透明/可解释的执行报告，错了能方便溯源重试，不能停留在“噱头式生成”。
**安全/合规/隐私处理能力**
特别是B端，agent产品要能自动处理权限、数据隔离、异常兜底，这些才能上企业主战场。
**生态开放 & 插件/工具集成能力**
畅通无阻地接别的API、业务系统，成为现有IT生态的核心流量入口。通用且易部署到任何地方。
